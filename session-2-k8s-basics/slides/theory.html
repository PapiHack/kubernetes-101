This is the slide the whole course hangs on. You never tell Kubernetes how to do something; you tell it what you want and it works to make that true. Everything else — Deployments, Services, rollouts — is this idea wearing different clothes.

The reconciliation loop

Controllers
Every line in the right-hand column of slide 3 is one of these loops. This is also why deleting a Pod "doesn't work" in Lab 3 — it isn't magic, it's a loop. Promise them the delete-a-Pod demo now; it is the wow moment of the whole course. A thermostat is the analogy the official docs use, and it lands well.

The cluster: a brain and some muscle

This is your cluster: docs/kind-config.yaml builds one control-plane node and two workers. Run kubectl get nodes in Lab 1 and count them — three lines, and the control plane is the one labelled control-plane.
Cluster components · Nodes
Trace the arrows, do not list the boxes. Start at `kubectl`: one arrow, one door — every request from anyone, you or a component, goes to the API server, and nothing in the cluster talks to anything else. That single fact explains RBAC, audit logs and why the API server is the thing you make highly available. Then the three things hanging off it, each its own colour: etcd is drawn as a database on purpose — it is the only place state is kept, and the API server is the only thing allowed to touch it (back up etcd and you have backed up the cluster). The scheduler only answers "which node?" — it picks, it does not start anything. The controller manager runs the loops from the previous slide. Then the arrows down: the control plane decides, the workers run. On each worker the kubelet is teal like the API server, and that is the point — it is the one piece on the node that talks to it, pulling its work rather than being pushed. kube-proxy does networking, the runtime actually starts containers, the Pods are the payload. Keep each component to one sentence; they need the shape, not the details. In production the control plane is 3 nodes for HA. Our kind config builds 1 control-plane + 2 workers, so this picture is literally their cluster — have them run `kubectl get nodes` in Lab 1 and match the three lines to the boxes. (A default `kind create cluster` with no config makes a single node playing both roles; mention it only if someone skipped the config file.) "Master" is the older name they will still meet in blog posts and in the `node-role.kubernetes.io/control-plane` label.

What happens when you run kubectl apply

kubectl never talks to a node. Only to the API server.

This is the slide that makes the previous one concrete. Two things to land: (1) `apply` returning "created" means *stored*, not *running* — that gap is why `kubectl get pods` shows Pending for a moment, and why a broken image still applies cleanly and only fails later; (2) nothing in the chain talks directly to anything else — every component reads and writes through the API server. That is also why RBAC and audit logging live there (Session 4).

Kubernetes never runs a container on its own. It runs a Pod.

The bridge slide. Point at the two `hello-k8s:1.0` strings: it is literally the image they built in Session 1, unchanged — nothing about the container had to be adapted for Kubernetes. What changes is who decides: the docker command names a machine (yours) and a host port; the manifest names neither. The smallest thing you can ask a cluster for is not a container — it is a Pod.

The Pod, field by field

Always scheduled to one node, never split across two — all the containers, or none. In this course: one container per Pod, always.
Pods
Left and right are the same Pod — walk a frame, then point at what it drew. apiVersion/kind says which API type (teal → the box is a Pod); metadata is who it is (violet → the name chip, and those labels are the glue Services pull on next week); spec is what you want (amber → the containers). Three things to land. (1) The four top-level keys — see them once, recognise them forever; slide 14 comes back for spec vs status. (2) The dash on `- name:` makes `containers` a list, which is the commonest beginner error in this deck and what slide 15 drills — the second dash here is the whole reason a sidecar is possible. (3) A Pod is a wrapper, not a container: one IP for the whole Pod, so the two reach each other on `localhost`, and they share volumes. Name the sidecar pattern — a log shipper or a proxy beside the app — but do not explore it; every lab in this course is one container per Pod. This manifest reappears on slide 12 as a Deployment's `spec.template`, so tell them to remember its shape.

Deployments
Every box is the reconciliation loop from slide 5 doing its job — say that explicitly, it is the moment the course's central idea pays off. Lab 3 demonstrates boxes 1 and 2 live; box 3 and 4 are Session 3's hands-on. Point out the last panel: they do not learn a new YAML dialect, the Pod spec they just read moves under `template:` untouched.

Deployment → ReplicaSet → Pods

You touch the outer box. It creates the ones inside.

ReplicaSet
Left and right are the same three objects — walk a frame in the YAML, then point at the box it produced. Then land the one line that matters: spec.template IS a Pod manifest — the same fields they wrote by hand on slide 8, now embedded. Once that clicks, a Deployment stops being a new thing to learn and becomes a Pod with two wrappers. The ReplicaSet frame is the pair (count + selector) plus the template it stamps out; point at the frame edges, not the text. Two controllers, two questions, two loops — that division of labour is the whole design. They will never create a ReplicaSet by hand, but they will see one in `kubectl get all` named `hello-deploy-7d9f8c`, and its Pods named `hello-deploy-7d9f8c-x4k2p`: each name extends its parent, which is how you read that output. That indirection is what buys rolling updates and instant rollbacks, which is the next slide.

Rolling update: nobody notices

The v1 ReplicaSet is kept at 0 replicas, not deleted. That is what makes a rollback instant.
The Deployment does not edit Pods — it creates a second ReplicaSet and shifts the counts, one Pod at a time. Two knobs govern the shape: maxUnavailable and maxSurge (`kubectl explain deployment.spec.strategy`). Do not run the commands here — Session 3 does `set image`, `rollout status` and `rollout undo` hands-on. What they need today is the picture and the reason the old ReplicaSet sticks around. Honest footnote for later: "no downtime" also needs readiness probes, which is Session 3.

Objects in Kubernetes
Four fields, every time: apiVersion (which API group), kind (what type), metadata (who it is), spec (what you want). See it once, recognise it forever. The two halves are the two sides of the reconciliation loop, written down. Show `kubectl get pod hello-pod -o yaml` live so they see both at once.

Labels are the glue

spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello      # which Pods do I own? ─┐
  template:                             │ must be
    metadata:                           │ identical
      labels:                           │
        app: hello  # ─────────────────────┘
Selector ≠ template labels is the #1 beginner bug. We break it on purpose in Session 4.
Labels and selectors · kubectl get pods -l app=hello --show-labels
Kubernetes has no foreign keys — objects find each other by matching labels, all the way down. A ReplicaSet owns the Pods matching its selector; a Service (next week) sends traffic to the Pods matching its selector. Nothing is wired by name. Point at the unmatched grey Pod: it is not broken, it is simply not part of this set. That one picture explains ReplicaSet ownership, Service endpoints, and every "my Service returns nothing" bug they will hit in Session 4.

Namespaces: folders for most objects

kubectl get pods -A                              # every namespace at once
kubectl -n kube-system get pods                  # there is your control plane
kubectl api-resources --namespaced=false    # the ones with no namespace
Two hello Deployments can live in two namespaces without clashing — names are unique within a namespace. Cluster-scoped objects have nowhere to hide: one Node, one StorageClass name for the whole cluster. A folder, not a security boundary by itself.
Namespaces
Keep this to two minutes. Every object you create goes into a namespace whether you name one or not — you have been using `default` all along. Used for teams, environments, and to scope quotas and RBAC (Session 4). The namespaced/cluster-scoped split is the half beginners never get told: the objects they will write all week are namespaced, but the cluster's own furniture — Nodes, PersistentVolumes, StorageClasses, ClusterRoles, and Namespace itself — is not, which is why `kubectl -n demo get nodes` quietly ignores the `-n`. `kubectl api-resources --namespaced=false` is the answer to every "is this one namespaced?" question; show it live rather than listing the objects. Thirty seconds on this — it pays off in Session 3 when PVC (namespaced) meets PV (not). The payoff is immediate: in Lab 1 they run `kubectl get pods -A` and finally see the control plane components as ordinary Pods in kube-system — the architecture slide made real. Warn them about the classic beginner moment: `kubectl get pods` shows nothing because the thing they created is in another namespace. DNS follows the same split (`backend.demo.svc.cluster.local`) — Session 3 uses that.
