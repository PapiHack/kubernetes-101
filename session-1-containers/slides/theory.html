An application is never just your code: it is also a runtime at a specific version, system libraries, environment variables, and assumptions about the OS. Containers solve this by shipping the app AND its environment as one unit. Ask the room who has lived this.

A container is just a process

No second OS. Isolated, not hidden.

What is a container?
A container is a normal process that has been given a restricted view of the world. Two Linux features do it: namespaces (what a process can see) and cgroups (how much it can consume). Proof of "isolated, not hidden": run `ps aux` on the host and you can see the containerised process listed like any other.

Virtual machine vs container

Containers vs virtual machines
The visual point: the repeated Guest OS blocks are the whole difference — size, boot time, density (a handful of VMs per host vs dozens to hundreds of containers). VM isolation is hardware-level and stronger; container isolation is kernel-level and good. Not a competition: most production clusters run containers INSIDE VMs and take both. Ask the room: why would anyone still use a VM? Stronger boundary, different kernels, regulatory requirements.

What is an image?
Image = filesystem + metadata (which command to run, which port, which user). Container = a running instance with a thin writable layer on top; started, stopped, deleted, cheap and disposable. Class and object. The warning slide-lands in Session 3 as PersistentVolumeClaims.

Images are stacked layers

Change a line → everything stacked on top of it rebuilds.

Understanding image layers
This is why dependencies are copied BEFORE the source code: edit one line of app.py and pip install would re-run on every build if the order were reversed. Practical rule: what rarely changes at the top of the Dockerfile, what changes constantly at the bottom. Walk the numbers once, out loud: line 1 is the FIRST thing you write and becomes the BOTTOM layer; line 5 is the last thing you write and sits on top. Let them find the pairs themselves: ask "where did line 1 go?" and wait — the colour and the number answer it, and the answer is the bottom of the stack. The file reads downward while the image builds upward, and that inversion is what makes "everything above it rebuilds" sound backwards until you have seen it once. The palette runs cool to warm on purpose: the teal base is cached and free, the red top is rebuilt on every code change. Demo idea: build twice, show the "CACHED" lines.

A Dockerfile, split in two

Build time — makes the image

FROM python:3.12-slim
WORKDIR /app

Run time — starts the container

RUN builds.
CMD starts.

Dockerfile reference · Dockerfile concepts
Walk the left column line by line: base image, working directory inside the image, copy files from your machine into the image, run a command at build time, EXPOSE is documentation only. The one distinction to hold onto is the right column: RUN happens while building, CMD happens when a container starts. CMD is a default and is overridable (`docker run img sh`); ENTRYPOINT fixes the executable and appends arguments instead. For this course: use CMD. Kubernetes overrides these with `command:` (= ENTRYPOINT) and `args:` (= CMD) — worth a mention in Session 2.

Source → running container

docker build -t hello-k8s:1.0 app/
docker run -d -p 5000:5000 hello-k8s:1.0
docker ps · docker logs · docker exec -it <name> sh
No -p → unreachable from your browser, even though it runs perfectly.
This is the single most common "my app is broken" moment in Lab 1 — it isn't broken, it just has no door. Show `docker ps` with and without the PORTS column filled in. Also demo docker exec -it <name> sh so they see it really is a little filesystem.

Build context
The context is the single most misunderstood part of docker build. That trailing dot is not "here", it is "ship this entire directory tree to the builder". Two consequences they will feel: builds crawl when .git or node_modules travel along, and secrets leak in through a careless COPY . . — which is why .dockerignore was on the habits list. Demo: add .git to .dockerignore and watch the "transferring context" line shrink.

Dockerfile reference
Do not recite this — it is a slide to photograph, and the wording matches the official reference so it looks familiar when they open it. Say the split once, using the When column: the build rows change the image's filesystem, the run rows only write metadata read when a container starts. Pair 1 of 3

COPY or ADD?

Same job — until you hand them something that isn't a plain file.

You point it at…COPYADD
a file or folder in your build context copies it copies it — identical
https://example.com/data.json not supported downloads it for you
a local app.tar.gz copies the archive, as an archive unpacks it into files 😲

Always COPY — unless you want that download, or that unpacking.

Read the table down the ADD column: the first row is why people think the two are interchangeable, the next two are why they are not. The third row is the one that bites — you meant to ship an archive and you got a directory, silently. ADD is not evil, it is just less predictable, which is why the rule is COPY by default and ADD only when one of those two behaviours is what you actually asked for. If they ask about downloading a file: RUN curl is usually better, because you control the failure and can clean up in the same layer.

Kubernetes renames both, and it is a classic trap: command: is ENTRYPOINT, args: is CMD.
Read the last row out loud — it is the entire lesson. Whatever you type after the image name replaces CMD, but is appended to ENTRYPOINT as arguments. So CMD is for "usually run this", ENTRYPOINT is for "this container IS this program". For this course, CMD is enough. The Kubernetes line is worth repeating next week when they meet command:/args: in a Pod spec.
Pair 3 of 3

ARG or ENV?

Neither is a secret — docker history reads both. A password passed at build time stays in the image.
One rule, and the layout says it: the ARG bar stops at the wall, the ENV bar runs straight through it. ARG is for build knobs (a version, a mirror URL); ENV is for configuration your app reads. The warning is the callback to "never bake secrets" — and now they can name the mechanism rather than just obeying the rule. In Session 3 Kubernetes gives them the real answer for configuration: ConfigMaps and Secrets, set outside the image entirely.

The container dies. So does everything it wrote.

named volume — Docker owns it 
docker run -v app-data:/data myapp

Lives in Docker's own storage; docker volume ls finds it. This is the one for real data.

bind mount — a folder on your machine 
docker run -v "$(pwd)":/app myapp

Your files, live inside the container. Edit and reload with no rebuild — the dev-loop trick.

Session 3 does this again, one level up: a Pod's filesystem dies with the Pod, and a PersistentVolumeClaim is how you ask for storage that doesn't.
Volumes · Bind mounts
The docs put it in one sentence: “When a container is destroyed, the writable layer is destroyed with it.” Most people learn that the expensive way. Read the left column out loud and make the point that the second container is not the same container — it is a fresh one from the same image, which never had the file. Then the right column: the volume is not inside the container, it is beside it, and the container just mounts it at a path. Two flavours, and the choice is almost always obvious: a named volume for data you care about (Docker manages where it lives), a bind mount when you want your own folder visible inside — that is the edit-and-reload dev loop, not a production pattern. Two things worth saying if they ask: `--mount` is the long explicit form the docs now prefer, `-v` is the short one everyone types; and `--rm` deletes anonymous volumes but leaves named ones alone. Do not go near volume drivers or NFS. The bonus lab (`exercises/02-bonus-volumes.md`) is three commands that prove all of this — point fast finishers at it after Lab 2, and tell everyone else it is worth ten minutes at home, because Session 3's PVC lab assumes this idea.

Building best practices
Small bases = faster pulls and less attack surface. Secrets in an image are readable by anyone who pulls it. .dockerignore keeps .git/ and node_modules/ out of the build context. One concern per container: a web server and a database are two images. Logging to stdout matters more than it looks — it is the contract every orchestrator relies on.
